# Intermediate Storage Layer for Direct UNDL API Ingestion

## Motivation

The app currently depends on a third-party bulk CSV export of GA voting data (resolved dynamically
via the UNDL API's "latest file for record ID" mechanism, see `config/data_sources.yaml`). New
resolutions only become available once that export is regenerated by someone else, which introduces
latency outside our control.

The UNDL API can also be queried directly for individual resolutions/voting records, without waiting
for a bulk export. The goal is a system that polls the API twice a day for new/updated resolutions
and keeps a durable, incrementally-updated storage layer that the app reads from — rather than the
app rebuilding everything from a bulk CSV on every deploy.

## Architecture

```
[Ingestion job — VM cron, 2x/day]
        │  upserts resolutions/votes AND thesaurus/subject data
        │  + writes run log/cursor
        ▼
[Postgres — same instance as Rybbit, separate database]
   - source-of-truth resolution/subject/vote tables
   - ingestion run log + last-successful cursor
        │  read (on start, and on periodic in-process reload)
        ▼
[App process(es)] — reloads in-memory DataFrames + precomputed
   NumPy arrays (vote_bool_arrays, multilateral_scores, ...) from
   Postgres; stateless across restarts; any number of replicas can
   point at the same Postgres independently; app never talks to
   UNDL directly — Postgres is the only thing it reads from
```

App/UNDL decoupling is deliberately total, not just for votes. The thesaurus SKOS fetch +
subject/closure/broader processing (today done in-app by `DataRepository` at cache-miss time) moves
into the same ingestion job. Reasoning: leaving it in-app would only half-fix the deploy-downtime
problem this project exists to solve (CLAUDE.md already calls out multi-minute startup rebuilds), and
would leave two different freshness/dependency models coexisting in one app. Thesaurus changes far
less often than resolutions, so this doesn't need the twice-daily cadence itself — but it's simplest
to run it as an idempotent step in the same job (skip the write if nothing changed) rather than
standing up a second schedule for something this infrequent.

## Decisions

| Area | Decision | Why |
|---|---|---|
| Ingestion job location | Cron on the existing VM | Reuses current infra; will be revisited when infra moves to UN hosting |
| Storage layer | Postgres, same instance as Rybbit, **separate database** within it | No new service to run; isolation from Rybbit's schema/lifecycle avoids coupling to an unrelated tool's maintenance |
| Storage contents | `resolution_outcomes` (one row per resolution, any body) + `resolution_votes` (normalized long table: one row per resolution x country x vote, not the wide one-column-per-country shape used in memory) + `subject`/`subject_broader`/`subject_closure`/`resolution_subject` (thesaurus hierarchy + per-resolution subject assignments) + `ingestion_runs` log (timestamps, counts, success/failure, QA issue summary) | Long/normalized vote table avoids schema migrations when new countries appear, and matches how the source notebook already separates resolution-level metadata from individual votes — see Postgres Schema section below |
| Multi-body naming (`source_dataset`) | Tables are named body-agnostically (`resolution_outcomes`/`resolution_votes`, not `ga_*`), with a `source_dataset TEXT` column (`'GA'`/`'SC'`/`'HRC'`, ...) on `resolution_outcomes` mirroring dataset-specific fields (GA's `session`/`committee_report`/`agenda_title` vs. SC's `agenda`/`description`/`modality`) as nullable side-by-side columns | Matches the unified-schema pattern the app already implements in `app/un_data_stream/data/merger.py` (already proven for GA+SC, SC fetcher/processor already exist though dormant) — reusing it now costs nothing since nothing's built yet, and avoids a rename/migration once SC/HRC ingestion is actually turned on |
| Unmatched subject strings | Not stored as rows (e.g. no `resolution_subject` row with a null `subject_id`) — logged to `ingestion_runs.issues_detail` instead, same QA pattern as name/vote-count mismatches | A raw subject string that didn't match anything in the thesaurus is useless for filtering (nothing will ever query for a null `subject_id`); treating it as a QA finding surfaces it as actionable instead of leaving inert rows. **Revisit later**: may want to retain raw unmatched strings as queryable rows at some point — deliberately deferred, not decided against |
| Country name in `resolution_votes` | Not stored. `country_code` only; the API's per-vote name is used transiently at ingestion time as a QA check against our existing name-resolution lookup (`app/data.py`), with mismatches logged to `ingestion_runs.issues_detail` | Avoids a second, possibly-drifting source of truth for country names we already resolve elsewhere; still gets the data-quality value without redundant storage |
| Vote-count QA | `resolution_outcomes.total_yes/total_no/total_abstentions/total_non_voting/total_ms` kept as reported by the source (not derived), cross-checked against `COUNT(vote=...)` over `resolution_votes` at ingestion time, mismatches logged to `ingestion_runs` | Mirrors the existing notebook's own QA step (3.3); catches source data issues rather than silently trusting or silently discarding the reported totals |
| `modality` derivation | Not a raw field — derived at ingestion time from three raw signals (`967` presence, raw `590.a`, raw `591.a`), same three-way output and QA fallback as the source notebook's own step 2.6 (`"Vote, recorded"` / `"Vote, non-recorded"` / `"Without a vote"`, `"Issue"` for unclassifiable combinations, logged to `ingestion_runs.issues_detail` rather than silently guessed) | Confirmed via `compile_votes_ga_run.py` that the published CSV's `modality` column is already this derived value, not a raw MARC field — replicating it is what "minimally copy the CSV" actually requires here, not passing through `590.a`/`591.a` directly |
| Low-count code/name combinations QA | In addition to the exact-duplicate name check above, group `resolution_votes` by `(country_code, ms_name)` at ingestion time and surface the rarest combinations (source notebook step 3.4, threshold tuned per dataset size) | Catches likely transcription errors and rare/retired-code variants (confirmed useful in the prototype: surfaced real historical variants like `CZE`→`CZECH REPUBLIC` vs. current name) that an exact-duplicate check alone wouldn't flag |
| Row bookkeeping | `inserted_at` (our own write time, excluded from `ON CONFLICT DO UPDATE`) **plus `source_updated_at`** on `resolution_outcomes`, populated from the UNDL API's own per-record `updated` timestamp — not a generic app-side `updated_at` audit column | Confirmed via the live API: every record carries `created`/`updated` fields, and `sort=updated&direction=desc` is a real, working query parameter. This is upstream data, not row-bookkeeping we invent — it's exactly the signal needed to (a) drive incremental fetch (page until a record's `updated` drops to/below our last watermark) and (b) detect retroactive corrections (re-upsert whenever the fetched `updated` is newer than what we stored) — see the new "Querying the UNDL API for voting data" section below |
| Reload marker | `MAX(completed_at) FROM ingestion_runs WHERE status = 'success'` — not derived from row-level timestamps | Row-level timestamps could reflect a partially-failed run; the marker should only advance once a full, QA'd batch completed successfully |
| Backup policy | None for now | Storage layer is a rebuildable cache of UNDL's data, not ground truth (ground truth lives at the UN); a full rebuild is acceptable if lost. **This assumption breaks if we ever store anything non-recoverable** (e.g. manual corrections/annotations) — revisit backups if/when that happens |
| App query performance model | Unchanged: in-memory DataFrames + precomputed NumPy arrays | Vectorized broadcasting over the full in-memory dataset is what makes `query_engine.py` fast at this data size; moving to live per-request DB queries would be a performance regression, not an improvement, for a dataset this small |
| App/storage decoupling | App reloads its in-memory copy from Postgres (on start, and periodically in-process) rather than only picking up new data on redeploy; any number of app replicas can point at the same Postgres independently | Gets "fresh data without redeploy" and "frontend scales independent of storage" without sacrificing in-memory compute speed |
| Reload mechanism | **Option A: each app process/worker polls a cheap "last updated" marker in Postgres on a timer (~15–30 min) and reloads + atomically swaps its in-memory copy if newer** | Self-contained, no new coupling between ingestion job and app, no new attack surface, naturally resilient (failed checks just retry). Rejected alternatives: (B) ingestion job pushes a reload trigger to the app — adds coupling, needs securing, and must fan out to every replica; (C) scheduled restart of the app container — simplest, but causes real (if brief) downtime and doesn't decouple freshness from a disruptive restart |
| Historical backfill | Existing bulk-CSV pipeline stays, used once to seed Postgres; incremental ingestion job takes over from there | No need to re-derive decades of history via the new per-record API path |
| Ingestion job repo | **Separate repo** from `policy-pulse`, not a monorepo | Different lifecycle (VM cron vs. gunicorn web app), different dependency sets (parsing/HTTP libs vs. Dash/Plotly), independent deploy path (doesn't need GitHub Actions/Watchtower/Docker the way the app does) |
| Code sharing between the two repos | **None, deliberately.** No shared package/git-dependency between `policy-pulse` and the ingestion repo | Under the "full decoupling" decision above, the app stops running thesaurus/subject-matching processing entirely once migrated — that logic isn't shared between two live consumers, it just *moves* into the ingestion repo wholesale. The copy staying in `app/un_data_stream` is used once for the historical backfill (as-is, unmodified) and isn't an ongoing dependency. The ingestion job will match against whatever shape the live per-record API actually returns (unknown until we have access), so even the reusable-looking grammar (thesaurus SKOS→table processing, subject-string matching) likely needs adapting anyway — cheaper to port it by hand once the real input shape is known than to maintain a cross-repo package for logic this small |
| API layer between app and Postgres | **Not now.** App keeps talking to Postgres directly (per the reload-mechanism design above); no separate query/API service | There's exactly one consumer today (this app) — a service boundary earns its cost when multiple things need to evolve independently, which isn't the case yet. Postgres already provides the actual decoupling wins wanted ("fresh data without redeploy", "storage independent of frontend"); an API layer on top wouldn't add more of that, just another process to deploy/monitor running logic that's currently free to live in the app. **Revisit if**: (a) a second consumer of this data shows up (public API, another dashboard, mobile client), or (b) running multiple app replicas becomes wasteful because each independently holds a full private in-memory copy — at that point, extracting `ResolutionQueryEngine` into its own service (still in-memory/vectorized, just in a separate process) becomes a clear win rather than speculative |

## Postgres Schema (voting data)

Normalized long table for votes (one row per resolution x country), split from resolution-level
metadata — mirrors the existing source notebook's own `ga_outcomes`/`ga_votes` split
(`notebooks/voting-preprocessing/python_processing/notebooks/compile_votes_ga_run.py`), but
de-duplicated (the notebook's flat CSV repeats resolution metadata on every vote row; we don't need
to here). Tables are named body-agnostically with a `source_dataset` discriminator, matching the
unified-schema pattern `app/un_data_stream/data/merger.py` already implements across GA/SC in-app
(see "Multi-body naming" decision above) — GA is the only body actually ingested for now, but the
shape doesn't need to change when SC/HRC ingestion gets turned on later.

```sql
CREATE TABLE resolution_outcomes (
    undl_id           TEXT PRIMARY KEY,      -- UNDL control number (see open question below)
    source_dataset    TEXT NOT NULL,         -- 'GA' | 'SC' | 'HRC' | ...
    resolution        TEXT,                  -- e.g. 'A/RES/78/1'
    date              DATE NOT NULL,
    modality          TEXT NOT NULL,         -- derived, not raw MARC — see "modality derivation"
                                              -- decision above: 'Vote, recorded' | 'Vote, non-
                                              -- recorded' | 'Without a vote'
    draft              TEXT,
    meeting            TEXT,
    subjects           TEXT,                 -- raw `991.d` values joined for reference/QA display;
                                              -- resolution_subject below is what's actually queried
    vote_note          TEXT,
    total_yes          INTEGER,
    total_no           INTEGER,
    total_abstentions  INTEGER,
    total_non_voting   INTEGER,
    total_ms           INTEGER,
    undl_link          TEXT,
    -- GA-specific (null for other bodies)
    title              TEXT,
    session            INTEGER,
    committee_report   TEXT,
    amended_draft      TEXT,
    related_documents  TEXT,
    agenda_title       TEXT,
    -- SC-specific (null for GA) — field names TBD once SC ingestion is actually designed
    description        TEXT,
    agenda             TEXT,
    source_updated_at  TIMESTAMPTZ NOT NULL, -- from the API's own `updated` field; drives incremental
                                              -- fetch cursor + retroactive-correction detection
    inserted_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE resolution_votes (
    undl_id      TEXT NOT NULL REFERENCES resolution_outcomes(undl_id),
    country_code TEXT NOT NULL,
    vote         TEXT NOT NULL CHECK (vote IN ('Y','N','A','X')),
    inserted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (undl_id, country_code)
);

CREATE TABLE ingestion_runs (
    id                   SERIAL PRIMARY KEY,
    source_dataset       TEXT NOT NULL,      -- 'GA' | 'SC' | 'HRC' | 'thesaurus' | ...
    started_at           TIMESTAMPTZ NOT NULL,
    completed_at         TIMESTAMPTZ,
    status               TEXT NOT NULL,      -- 'success' | 'failed' | 'partial'
    resolutions_upserted INTEGER,
    votes_upserted       INTEGER,
    issues_count         INTEGER DEFAULT 0,
    issues_detail        JSONB                -- e.g. name-mismatch / vote-count-mismatch findings
);
```

At app load/reload time, `resolution_outcomes` + `resolution_votes` get pivoted into the wide,
in-memory shape `query_engine.py` already expects (`country_columns` + per-vote-type boolean NumPy
arrays) — the normalized-long shape is a storage/ingestion convenience, not what's queried at
runtime.

### Postgres Schema (subject hierarchy)

Mirrors what `app/un_data_stream/processors/thesaurus_processor.py` and
`processors/ga_processor.py` already produce today — the ingestion job reuses this exact processing
logic (same SKOS traversal, same subject-string matching grammar), just runs it against Postgres
instead of in-app memory:

```sql
CREATE TABLE subject (
    subject_id     TEXT PRIMARY KEY,      -- SKOS concept/scheme URI
    label_en TEXT, label_es TEXT, label_fr TEXT, label_ar TEXT, label_ru TEXT, label_zh TEXT,
    alt_labels_en TEXT, alt_labels_es TEXT, alt_labels_fr TEXT, alt_labels_ar TEXT,
    alt_labels_ru TEXT, alt_labels_zh TEXT,
    node_type      TEXT NOT NULL          -- 'concept' | 'scheme'
);

CREATE TABLE subject_broader (       -- direct SKOS `broader` edges only, for tree navigation
    parent_id TEXT NOT NULL REFERENCES subject(subject_id),
    child_id  TEXT NOT NULL REFERENCES subject(subject_id),
    PRIMARY KEY (parent_id, child_id)
);

CREATE TABLE subject_closure (       -- full transitive ancestor/descendant pairs, for hierarchy filters
    ancestor_id   TEXT NOT NULL REFERENCES subject(subject_id),
    descendant_id TEXT NOT NULL REFERENCES subject(subject_id),
    depth         INTEGER NOT NULL,
    PRIMARY KEY (ancestor_id, descendant_id)
);

CREATE TABLE resolution_subject (
    undl_id    TEXT NOT NULL REFERENCES resolution_outcomes(undl_id),
    subject_id TEXT NOT NULL REFERENCES subject(subject_id),  -- only confirmed matches
    PRIMARY KEY (undl_id, subject_id)
);
```

Per-resolution subject assignment reuses `GAResolutionProcessor`'s matching grammar, adapted to the
API's actual shape (see "Querying the UNDL API for voting data" below): each repeated `991.d` value is
already one subject string — no `|`-split needed, that was an artifact of the notebook's flattened
CSV, not the source. Each `991.d` value is still split on `--` keeping only the part before it,
lowercased + stripped, then exact-matched against every `label_*`/`alt_labels_*` column in `subject`.
Strings that don't match anything are **not** written as a `resolution_subject` row — see the
"Unmatched subject strings" decision above.

### Implementation details identified while designing the reload mechanism

- gunicorn currently runs with `--preload` (data loaded once in the master before fork; workers share
  it via copy-on-write). That sharing only applies to memory that exists **at fork time** — once each
  worker independently reloads on its own timer (Option A), the reloaded data is a fresh, private
  allocation in that worker's process, not shared with siblings. `--preload` remains valuable for
  faster/fail-fast startup, just not for steady-state memory after the first in-process reload.
- Any Postgres connection/pool the app uses must be created **after fork** (e.g. lazily on first use,
  or in a gunicorn `post_fork` hook), not at module-import time before `--preload` forks workers —
  sharing a single forked DB connection across multiple worker processes causes corruption/undefined
  behavior.

## Querying the UNDL API for voting data

Confirmed against the live API (`https://metadata.un.org/editor/api/marc/bibs/...`) — no auth was
required for these read endpoints in ad hoc testing (see the "still open" auth/rate-limit note below).

**1. Search/list endpoint** — finds voting-data records, paginated, sortable by last-modified:

```
GET https://metadata.un.org/editor/api/marc/bibs/records
    ?search=989:Voting%20Data
    &subtype=all&format=brief
    &sort=updated&direction=desc     # or asc
    &start=<offset>&limit=<page size>
```

Response `data` is a list of `{_id, symbol, date, title, url, ...}`; `_id` is the numeric UNDL control
number (→ `undl_id` — matches the notebook's `digitallibrary.un.org/record/{undl_id}` link format
exactly, confirming it as a stable, real identifier, not a guess), `symbol` is the resolution symbol
(`A/RES/80/308`), `url` is the per-record detail endpoint for that resolution. `_links._next` gives
the next page directly.

No server-side date/updated-range filter exists — a `updated:[... TO ...]` search clause 500'd.
Incremental fetching therefore has to **page through `sort=updated&direction=desc` and stop once a
record's `updated` drops to or below the ingestion job's last watermark**
(`MAX(source_updated_at)` from `resolution_outcomes`, or `ingestion_runs.completed_at` for the run
marker), rather than filtering via a query param.

**2. Per-record detail endpoint** — full record for one resolution:

```
GET https://metadata.un.org/editor/api/marc/bibs/records/{_id}
```

Response `data` has top-level `_id`, `created`, `updated` (→ `source_updated_at`), `created_user`,
`user`, plus MARC tags as keys. Cross-checked against the source team's own tooling —
`notebooks/voting-preprocessing/python_processing/datasets/votes_ga/map.json` (their MARC-tag map
for this exact dataset) and `src/unlibmd.py` (their extraction helpers) — which corrected some
initial guesses. Fields used by our schema:

| Tag/subfield | Example | → |
|---|---|---|
| `791.a` | `A/RES/80/308` | `resolution` |
| `791.c` | `80` | `session` |
| `992.a` | `2026-09-04` | `date` |
| `991.c` / `.d` (repeated, one pair per subject) | agenda title / subject string | `agenda_title` / one `resolution_subject` candidate per entry |
| `952.a` | `A/80/PV.114` | `meeting` |
| `996.a` | (rare — "peculiarities" notes) | `vote_note` |
| `996.b/c/d/e/f` | `164/8/9/12/193` | `total_yes/total_no/total_abstentions/total_non_voting/total_ms` |
| `245.a`+`b`+`c` | joined | `title` |
| `967` (repeated, one per country) | `a`=seq, `c`=ISO3 code, `d`=`Y`/`N`/`A` (**subfield absent entirely** for non-voting), `e`=English name | one `resolution_votes` row each (`d` missing → `X`) |

`993.a` is reused for four *different* concepts, disambiguated by the first indicator — a naive
"first `993.a` value" (this plan's original guess) happened to land on `draft` and silently missed
`committee_report` entirely:

| `993` indicator | Example | → |
|---|---|---|
| `ind1="2"` | `A/C.3/80/L.20/Rev.1` | `draft` |
| `ind1="3"` | `A/80/545` | `committee_report` |
| `ind1="6"` | (rare) | `amended_draft` |
| blank | `A/C.3/80/L.33/Rev.1` (rare — 2/300 in the sample) | `related_documents` — extracted by the source tooling too but actually dropped before either published CSV; kept here anyway as a deliberate deviation, see below |

`modality` is **not** a direct field mapping — see the "modality derivation" decision above. It's
computed from `967` presence plus two raw signals, `590.a` (`"Vote"` / `"Without Vote"`) and `591.a`
(`recording_modality`, e.g. `"RECORDED - No machine generated vote"` / `"ADOPTED WITHOUT VOTE"` /
text containing `"NON-RECORDED"`) — neither raw field is stored on its own, matching the source CSVs
(both are extracted by the source tooling but consumed by the derivation, not published).

Verified the `Y`/`N`/`A`/absent-means-`X` vote encoding against a resolution with real abstentions —
the `996` tally (`164/8/9/12/193`) reconciled exactly against the `967` breakdown, so this isn't
inferred from a single all-`Y` example.

**Subjects are not `|`-joined text at the source.** The notebook's flat CSV joins multiple subjects
that way when flattening; the raw API instead gives each subject its own repeated `991` entry
(subfield `d` still uses `--` as the within-subject hierarchy separator, e.g.
`HUMAN RIGHTS--INTERNATIONAL INSTRUMENTS`). The ingestion job should iterate the repeated `991.d`
values directly rather than reproducing the notebook's `|`-then-`--` split.

**Not stored, confirmed deliberately** (extracted by the source notebook too, but dropped before
either published CSV): `dhl_id` (`035.a`, metadata-editor id — also just absent from this API's
responses entirely, unlike the old `digitallibrary.un.org` XML API `unlibmd.py` targets), and raw
`recording_modality` (fully absorbed into the `modality` derivation, no reason to also keep it
raw). The agenda item *symbol* (`991.a`, e.g. `A/80/251`) isn't in `map.json` at all, so it's
assumed genuinely unneeded too.

**Stored despite the source CSVs dropping it**: `related_documents` — the one deliberate deviation
from "minimally copy the CSV". It's genuinely extracted by the source tooling (`map.json` defines
it) but never makes it into either published dataset. Kept as a nullable column anyway since it's
plausibly useful for a future "related resolutions" feature and costs nothing to carry.

**Search query needs a body filter.** `search=989:Voting Data` alone also matches SC/HRC
voting-data records, not just GA — the source notebook's own query combines
`c='Voting Data'` with `p='981:"General Assembly"'`. Since `resolution_outcomes.source_dataset` is
set by the ingestion job itself (per body-specific ingestion logic), not derived from the response,
the search query needs the equivalent filter (`AND 981:"General Assembly"`) to avoid silently
mislabeling a non-GA record as `'GA'`.

## Open questions (TBD)

- **Handling deleted/withdrawn records**: the `updated`-sort-and-watermark approach (above) only
  surfaces records that still exist and were touched. Whether UNDL ever fully removes/withdraws a
  voting-data record, and if so how (or whether) that's detectable, is unverified.
- **Auth/rate limits**: no authentication was required and no rate-limiting was hit in ad hoc
  exploratory testing, but this hasn't been verified under the actual twice-daily production access
  pattern — worth confirming before relying on it.
- **Ingestion job Postgres credentials**: how they're provisioned and kept out of version control.
- **Ingestion repo deploy mechanics**: does it need its own CI/Docker image, or is a plain script
  invoked by VM cron (pulling from git, or copied manually) enough at this scale?
- **Retaining unmatched subject strings**: for now they're only logged as a QA finding, not stored as
  queryable rows (see decision above) — may want to revisit and retain them later.
